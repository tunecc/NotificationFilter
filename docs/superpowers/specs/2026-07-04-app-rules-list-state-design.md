# 应用规则选择页首屏背景与状态一致性设计

## 背景

`NotificationFilterPrefs/NFPAppRulesListController` 负责展示“选择应用程序”的应用列表。当前用户反馈，在深色模式下第一次进入该页面时，列表底色会表现为偏灰；退出后再次进入，底色才恢复为预期的深色。

代码路径显示，该页面首次进入时会走 `beginInitialLoad`，先展示 loading 文案，再异步刷新应用列表；但该控制器没有显式设置 `tableView.backgroundColor`，而仓库中其他列表页已经统一使用 `systemGroupedBackgroundColor`。这导致首屏表现依赖系统默认背景，容易在首次加载阶段出现和后续状态不一致的颜色。

此外，该页面当前只有 loading 占位，没有明确的空状态文案；搜索结果为空时也会直接显示空表格，反馈不够明确。

## 目标

- 修复深色模式下首次进入“选择应用程序”页背景偏灰的问题。
- 统一该页面在 `loading`、`empty`、`content` 三种状态下的背景表现。
- 为应用列表为空和搜索结果为空提供明确的空状态文案。
- 保持现有筛选、搜索、下拉刷新和点击进入应用规则详情的行为不变。

## 非目标

- 不改动其他列表页的状态实现。
- 不新增全局通用的空状态组件或共享 helper。
- 不为该页面新增错误态设计；底层应用列表提供者当前没有显式错误回传接口。
- 不调整应用列表排序、筛选规则或缓存策略。

## 当前问题

当前页面的状态切换逻辑分散在多个方法中：

- `viewDidLoad` 决定走缓存命中或首次加载路径。
- `beginInitialLoad` 直接设置 `tableView.backgroundView` 为 loading 文案。
- `refreshApplications:` 完成后直接清空 `backgroundView`。
- `reloadApplicationsFromCache` 只负责重载数据和刷新标题，不统一处理空状态。
- `updateSearchResultsForSearchController:` 只刷新过滤结果，不为“无结果”提供状态文案。

这些分散逻辑带来的直接问题：

- 首次加载时页面底色不受控。
- loading 和 content 的背景风格不一定一致。
- 空列表和无搜索结果时缺少明确反馈。
- 后续如果继续追加页面状态，现有分散写法仍然容易产生新的分支不一致。

## 设计概览

本次只在 `NFPAppRulesListController` 内收口状态管理，不引入共享抽象。

设计原则：

- 页面底色由 `tableView.backgroundColor` 唯一负责。
- `backgroundView` 只负责状态文案展示，不负责背景着色。
- 所有背景状态切换统一经过单一入口方法，例如 `updateBackgroundState`。
- 数据刷新、缓存加载、搜索筛选都不再各自直接操作 `backgroundView`。

## 状态模型

页面状态统一为三类：

```text
loading
empty
content
```

含义如下：

- `loading`：首次进入且尚未拿到应用列表，或用户主动下拉刷新后等待最新结果。
- `empty`：当前应展示的列表结果为空。
- `content`：当前有可展示的应用项。

`empty` 需要覆盖两种场景，但仍复用同一个状态入口：

- 应用列表本身为空。
- 已有应用列表，但当前搜索条件下没有匹配结果。

## 页面表现

### 背景颜色

在 `viewDidLoad` 中显式设置：

```objc
self.tableView.backgroundColor = [UIColor systemGroupedBackgroundColor];
```

这样无论是否命中缓存、是否处于 loading、是否刚完成异步刷新，底色都保持一致。深色模式下首次进入也直接使用正确的系统深色分组背景。

### Loading 状态

`loading` 状态显示一个居中的文案视图，例如“正在加载应用列表…”。该视图本身保持透明背景，文字颜色使用 `secondaryLabelColor`，避免与底色重复定义。

### Empty 状态

`empty` 状态显示明确文案，不再保留空白表格。建议区分两类文案：

- 应用列表为空：提示当前没有可展示的应用，可下拉刷新重试。
- 搜索结果为空：提示当前搜索条件下没有匹配的应用，可修改关键词或清除搜索。

实现上使用同一个空状态视图即可，内部提供标题和说明两段文案；当状态来源变化时，仅切换文案内容，不切换视图结构。

### Content 状态

有内容时清空 `backgroundView`，只显示正常表格内容。

## 状态切换时机

所有状态变更收口到统一入口。建议时机如下：

- `viewDidLoad`
  - 先设置统一底色。
  - 如果没有缓存，进入 `loading`。
  - 如果已有缓存，直接走数据重载，并由重载结果决定 `empty/content`。

- `beginInitialLoad`
  - 不再直接拼装零散背景逻辑，只切到 `loading` 并触发刷新。

- `refreshApplications:`
  - 开始刷新时进入 `loading`。
  - 刷新完成后，由 `reloadApplicationsFromCache` 统一决定下一状态。

- `reloadApplicationsFromCache`
  - 更新应用列表、规则数量、搜索过滤结果、标题副标题。
  - 根据当前应展示的数据结果统一切换到 `empty` 或 `content`。

- `updateSearchResultsForSearchController:`
  - 刷新过滤结果后，重新评估 `empty/content`。
  - 如果底层应用列表非空但过滤结果为空，显示“无搜索结果”类空状态。

## 文案要求

中文建议：

- Loading：`正在加载应用列表…`
- 空列表标题：`暂无可用应用`
- 空列表说明：`下拉可重新刷新应用列表。`
- 搜索无结果标题：`未找到匹配应用`
- 搜索无结果说明：`请尝试其他关键词，或清除当前搜索条件。`

英文文案在实现时同步补齐到 `en.lproj`，含义保持一致即可。

## 兼容性与边界

- 不改变现有的 `UISearchController`、过滤菜单和下拉刷新逻辑，只改变其触发后的背景状态呈现。
- 不依赖新的数据字段，也不修改 `NFPAppInfoProvider` 的接口。
- 如果刷新完成后缓存仍为空，页面应稳定停留在 `empty`，而不是再次回到未定义背景。
- 如果搜索中清空关键词，应从“无搜索结果”恢复到真实列表状态，而不是保留空状态文案。

## 测试与验收

至少验证以下场景：

- 深色模式下首次进入“选择应用程序”页，背景直接为正确的深色分组背景，不出现灰底。
- 退出后再次进入，同一页面背景与首次进入一致。
- 首次进入时 loading 文案、加载完成后的列表内容、空列表文案三种状态底色一致。
- 搜索命中结果时正常显示列表；搜索无结果时显示明确空状态文案，而不是空白表格。
- 下拉刷新时先显示 loading，刷新完成后正确恢复到 `content` 或 `empty`。
- 筛选按钮和点击进入单应用规则详情不受影响。

最低自动化门槛仍然是成功执行一次包构建；界面效果需要在 Settings 中手工确认。

## 风险与边界

- 由于该页当前没有错误态来源，本次不会区分“没有应用”和“加载失败”；两者都不会被伪装成成功内容页。
- 搜索空状态与原始空状态如果共用同一视图，必须确保文案在切换搜索词时同步更新，避免显示陈旧提示。
- 本设计只收口这一页的状态逻辑；其他列表页如果存在类似问题，需要独立评估，不在本次范围内。
